# Ladyflock Rebrand Plan

**Implementation proposal · `rebrand` · 27 November 2026**

Reviewed against Ladyflock baseline `81f53bea7f5` (branch `ladyflock`, `UI/Qt: Add Split View for tabs`). Source artwork lives outside the Git tree in `../Art/` (`Ladyflock-App-Icon.png`, `Ladyflock-Icon-Transparent.png`, `Ladyflock-Logo-Transparent.png`) and must be vendored or compiled into tracked repository assets during implementation.

Ladyflock owns the product, its releases, profiles and support channels. Ladybird supplies the engine through shared Git history. The rebrand should let a maintainer bring in a later rendering change together with its dependencies, even if Ladyflock has changed its name, version or release stage in the meantime.

**For an engine update, follow the [Ladybird source update procedure](UPSTREAM.md).** It covers choosing a revision, merging it into a temporary branch, comparing the previous Ladyflock build with the candidate and recording the result. The original Ladybird import is `be5e3ce8585ddb907c17fbdafcea11027a32ae6f`. The Ladyflock revision at the top of this plan is the baseline for this review. Future syncs advance from the last integrated Ladybird commit. Shipping binary updates will require Ladyflock-owned feeds and keys.

## 1. Identity model and merge boundary

| Identity | Value | Where it belongs |
|---|---|---|
| Product | `Ladyflock`, with a Ladyflock release stage where appropriate | App name, executable, window titles, prompts, notifications, menus, bookmarks, built-in pages and user documentation. |
| Product and engine attribution | `Ladyflock (Ladybird)` | Copyable diagnostics, CLI help and package descriptions. Show separate product and engine fields where the interface provides them. Retain upstream credits, copyrights and source references. |
| Compatibility and implementation | Existing Ladybird identifiers | Keep `namespace Ladybird`, CMake target `ladybird`, helper macros, resource paths, `window.ladybird`, protocol keys and wire behavior. Change an internal name when an identified product collision or interface requirement calls for it, with its consumers and tests in the same change. |

### Centralizing brand constants in code

Configure product metadata once so the generated C++ header, packaging templates and installed application agree. Keep the internal CMake project and target names. Use separate values for user-visible labels and the names sent over the wire.

| Value | Baseline | Proposed ownership and consumers |

## 2. Internal & web-facing identity: `Ladyflock (Ladybird)`

   - Page `<title>`: `About Ladyflock` (or `About Ladyflock Alpha`).

3. **CLI, Diagnostics, Crash & WebCompat Reports.**

### `User-Agent`, `Sec-CH-UA`, `WebCompat.json`, and `WebDriver`

Keep the existing web identity as the default for the rebrand. At this revision the UA contains `Ladybird/<version>` alongside the Chrome compatibility token. `Sec-CH-UA` is derived from the *effective request UA*. A site rule can remove `Ladybird/`, and a Firefox preset can suppress the hints entirely. Preserve those relationships as upstream updates the engine. Avoid pinning the current Chrome major or adding a Ladyflock token in engine code as part of a visual rename. `Ladyflock (Ladybird)` belongs in diagnostics. [UA definition](Libraries/LibWebCommon/Loader/UserAgent.h) · [Hint generation](Libraries/LibWeb/Fetch/Fetching/Fetching.cpp) · [Compatibility transforms](Libraries/LibWebCommon/Loader/SiteCompatibility.cpp) · [Site rules](Base/res/ladybird/WebCompat.json)

Verify a local echo of the default, hidden-token and overridden UAs, including a child frame. Compare the request headers with the identity exposed to script for the selected preset. Retain the existing assertions when the intended behavior is unchanged. A future proposal for public Ladyflock tokens needs its own compatibility and privacy evidence. [Client Hints fixture](Tests/LibWeb/Text/input/Fetch/user-agent-client-hints.html) · [Frame preset test](Tests/LibWebView/test-user-agent-preset-reaches-child-frames.py)

WebDriver matches an explicit `browserName` by exact equality. At baseline it reports `ladybird`. Keep that wire contract for existing clients during the rebrand, including `ladybird:headless`, `ladybird:enableTestHooks` and the gated `/ladybird/` endpoints. Independently point the launcher at the packaged **Ladyflock** binary. Test new sessions with an omitted name, an explicit supported name and an unsupported name. Launch through the existing WPT Ladybird adapter and confirm the controlled executable is Ladyflock. Changing the advertised name to `ladyflock` later requires a coordinated client/adapter update. [Capabilities.cpp](Libraries/LibWebCommon/WebDriver/Capabilities.cpp) · [WebDriver launcher](Services/WebDriver/main.cpp) · [WPT launcher](Meta/WPT.sh)

## 6. Profile, storage, and OS-coexistence plan

The default and named desktop profiles live under `<platform root>/Ladybird/Profiles/<name>` for config, data, cache and runtime. A custom `--profile-path` instead names **one absolute root** containing `config/`, `data/`, `cache/` and `runtime/`. Temporary profiles use another root. Android currently takes the legacy path. On Windows, config uses roaming AppData, data/cache use local AppData and runtime uses the temporary directory. `Application::create_profile` already compensates for a product suffix on Windows. [Profile.cpp](Libraries/LibWebView/Profile.cpp) · [Application.cpp](Libraries/LibWebView/Application.cpp#L910-L947) · [StandardPaths.cpp](Libraries/LibCore/StandardPaths.cpp)

- Put Ladyflock’s default and named profiles under Ladyflock’s own leaves in all four roots. Check the instance data directory, pre-profile crash-report fallback, DevTools profile and OS-specific path construction for accidental reads, writes or duplicated directory components. Retain the internal database filename inside a profile so an existing custom profile still finds its cookies and storage. [CrashReportStore.cpp](Libraries/LibWebView/CrashReportStore.cpp) · [FirefoxClient.cpp](Libraries/LibDevTools/FirefoxClient.cpp)
- Start with a fresh Ladyflock profile. A directory called `Ladybird` could belong to either product. Leave it in place and explain the fresh start in release notes. For an explicitly identified, self-contained custom profile, close its owner and test a separate copy with `--profile-path`. Pointing the flag at one of a default profile’s split OS roots is not an import. Any later importer needs explicit source selection, a consistent offline snapshot, schema checks and a fresh destination.
- Keep the runtime directory, startup lock, PID and socket paths scoped to the profile. The macOS handoff uses the canonical profile identity and PID. Preserve unique internal strings where possible. If a Mach service name changes, change registration and lookup together. Test second-launch URL handoff into the correct running product and profile, including while the other browser is open. [BrowserProcess.cpp](Libraries/LibWebView/BrowserProcess.cpp) · [Application.cpp](Libraries/LibWebView/Application.cpp) · [Qt Hub bootstrap](UI/Qt/Application.cpp)
- On Linux, treat Orca’s shared `orca-customizations.py` as user data. Give Ladyflock’s script directory, managed markers and Python wrapper independent ownership. The current wrapper saves a previous function in a module global. A second copy sharing that global can recurse when it delegates. Exercise both installation orders, repeated startup, third-party app fallback and preservation of the user’s existing content. [Qt installer](UI/Qt/Application.cpp) · [Orca bootstrap](UI/Qt/OrcaScripts/orca_customizations_bootstrap.py)

**Coexistence check.** In a disposable OS account, put distinguishable bookmarks and settings in each product’s default profile. Start both products normally, open separate local URLs by relaunching each, and restart both. Verify the correct running instance received each URL, the sentinel data stayed separate, and the original Ladybird data was never migrated or overwritten. Cover named and custom roots separately. Using only `--temporary-profile` for this check would mask a default-root collision.

## 8. Phased delivery and verification gates

Keep the five slices independently reviewable. Use disposable profiles until the profile and OS isolation work lands. A distributable build needs all applicable gates below.

| Phase | Implementation | Evidence for acceptance |
|---|---|---|
| 1. Product identity and services | Add product, stage and version metadata, keep the engine’s web-facing identity, gate updater and reporting paths. | Build development and release configurations. Set different product and compatibility versions and check `about:version`, final vs staged badges, package metadata, HTTP UA and Client Hints. Verify the default build with no overrides, the release checker disabled, and attempted opt-in without a Ladyflock feed/key. Exercise manual and queued report submission with synthetic data and record outbound destinations. |
| 2. Emblem and tinting | Add the canonical vector and optical treatments to the chrome, Version and Welcome. | Capture top tabs, sidebar tabs and everything-in-sidebar at 1× and 2×. Check Neutral and every named theme in light/dark, increased contrast, focus and inactive states. Compare the private mask separately. Check live accent changes in open tabs. Record contrast values for active regular-button foreground and native-size images for geometric legibility. |
| 3. Platform icons | Generate the assets from tracked sources and wire each one into its package. | Regenerate in a clean checkout. Inspect the built ICNS and, with the supported Xcode asset compiler, `Assets.car` plus actual macOS presentations. Inspect Linux’s installed desktop/notification icons and the browser favicon at tab size. Record native Windows icon coverage separately. |
| 4. Copy and product surfaces | Update menus, dialogs, first-run, settings, default bookmarks, feedback and documents. | Inspect the actual UI, including private windows and accessibility names, and copy diagnostics from `about:version`. Open the Ladyflock issue form and verify its fields locally or inspect the constructed URL. Confirm mixed old/new reports still open and saved bookmarks survive. |
| 5. Packaging, launch and profile isolation | Change output filenames, OS IDs, helper discovery and roots together as described in §§6–7. | Launch a staged install outside the source tree through its actual OS entry points. Exercise the build helper, WebDriver and packaged helpers, including the macOS helper-path tests for [ProcessReaper](Tests/LibWebView/TestProcessReaper.cpp) and [sandboxed helpers](Tests/LibSandbox/TestHelperSandboxes.cpp). Verify the signed macOS bundle and test Linux desktop/service files, notifications and package metadata. Run the side-by-side and second-launch checks in §6. Native Windows is experimental. WSL2 exercises the Linux build. Record each independently. [Build guide](Documentation/BuildInstructionsLadybird.md) |

Run the relevant suites from the actual build. For example, `TestSiteCompatibility` belongs to `TestLibWebCommon`, `TestDevToolsProtocol` to `TestLibDevTools` and `TestWebCompatReport` and `TestProfile` to `TestLibWebView`. Select each with `--suite` on its library executable and set `LADYBIRD_SOURCE_DIR` to that build’s source root. Exercise the registered `test-webdriver-addons` and `test-user-agent-preset-reaches-child-frames` browser tests. The separate `test-amo-ublock.py` check downloads real packages from Mozilla. Record it separately from deterministic local coverage. [Testing guide](Documentation/Testing.md) · [Extension compatibility](Documentation/Extensions/Compatibility.md)

### Rebrand review and future updates

Review `git diff --stat ladyflock...HEAD` **and the actual patch** for committed rebrand changes. Check `git status --short` and review pending files separately. Explain any engine edits by the interface they change. Preserve upstream copyright and license notices, internal resource paths and the WebUI bridge. Judge a rendering-library update on its behavior and dependencies, regardless of its diff size.

During implementation, keep the procedures and evidence in [UPSTREAM.md](UPSTREAM.md) current when a target, test or executable changes. For every sync, record the previously integrated Ladybird revision, incoming Ladybird revision, Ladyflock baseline, exact tested candidate, coverage on both revisions and unexplained differences. The ancestry check answers **which code was integrated**. The before-and-after results answer **which behaviors were exercised**.

## 9. Product decisions

| Decision | Recommendation for implementation |
|---|---|
| Permanent platform ID | Use the permanent ID `io.github.kayyo321.Ladyflock` for the GitHub project. macOS development builds append `.Development`. Verify the release ID and Linux desktop, D-Bus and AppStream entries agree with the packaged application. |
| Web-facing identity | Keep the baseline UA, Client Hints, site transformations and WebDriver contract during the rebrand (§2). Ladyflock owns its public product name, release number and release stage. |
| Neutral theme | Keep signature purple in Neutral and tint in the nine named themes. OS accent in Neutral would be a separate design change. |
| Version page | Keep the existing stacked layout with a scalable emblem, live heading and stage badge when applicable. The supplied horizontal lockup remains a design reference. |
| Existing installations | Start with a separate default profile, document where the old data remains, and test any explicit custom-profile reuse on a closed copy (§6). |
